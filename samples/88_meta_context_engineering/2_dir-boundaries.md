# Boundaries & Architecture: Autonomous Flight Delay Refund System

**Document Type:** Compiler Instruction Set — Architectural Invariants  
**Role:** World Builder (Software Architect)  
**Architecture:** DIR Topology C (Decision Ledger with Proof-Carrying Intents — DL+PCI)

---

## 1. System Topology
The system strictly implements **Topology C (DL+PCI)**. As defined in `1_intent.md` and the main DIR documentation (`../../docs/03-topologies/DIR_Topologies.md`), **DL+PCI** stands for **Decision Ledger with Proof-Carrying Intents**. This requires a hard, non-bypassable boundary between probabilistic reasoning (User Space) and deterministic execution (Kernel Space).

### 1.1 User Space (Untrusted)
- **Refund Policy Agent:** A Responsibility-Oriented Agent (ROA). Its sole responsibility is to evaluate `WorkingContext` and produce a `ProofCarryingIntent` (PCI).

### 1.2 Kernel Space (Trusted & Deterministic)
- **Context Compiler:** Assembles immutable `WorkingContext` and computes the `ContextSnapshotID`.
- **Proof Checker (DIM):** Deterministically validates the Agent's PCI.
- **Decision Ledger:** Append-only log of validated intents.
- **Execution Engine:** Triggers the payout API.

## 2. Hard Architectural Invariants

### 2.1 Strict I/O Isolation (Zero Agent I/O)
- The **Refund Policy Agent** MUST NEVER perform network I/O.
- The Agent MUST NOT import `requests`, `httpx`, `sqlalchemy`, `psycopg2`, `smtplib`, or any database/HTTP driver.
- The Agent MUST NOT fetch external state. All necessary data MUST be provided within the `WorkingContext`.

### 2.2 Deterministic Verification Boundary
- The **Proof Checker** MUST BE 100% deterministic. 
- It MUST NOT invoke any Large Language Models (no `openai`, `anthropic`, `litellm`).
- It MUST NOT make external API calls during validation. It verifies cryptographic signatures (`roa_signature`), recomputes evidence hashes, and performs structural validation.
- The **ResponsibilityContract** used for evidence hash validation MUST be read directly from the authoritative Agent Registry, never trusted from the Agent's payload.

### 2.3 JIT Verification & Drift Envelope
- Before execution, the system MUST perform Just-In-Time (JIT) Verification comparing current live state to the T0 `WorkingContext`.
- **Drift Envelope**: The execution MUST be aborted if any of the following have changed since T0:
  - `wallet_balance_eur`
  - `ticket_status`
  - Active `compensation_policy` version hash

### 2.4 Execution and Idempotency
- The **Execution Engine** is the ONLY component authorized to call the downstream Payout API.
- Execution MUST occur ONLY AFTER the PCI is successfully appended to the Decision Ledger.
- The Payout API call MUST include a deterministic Idempotency Key using the general formula: `SHA256(DFID + Step_ID + Canonical_Params)` where `Step_ID = "PAYOUT"` for the payout step. `Attempt_Number` MUST NOT be included in the key.

### 2.5 State Assembly
- The **Context Compiler** is responsible for hydrating all needed state (e.g., wallet balance, ticket info, policy rules) from the Context Store before invoking the Agent.
- The Agent operates exclusively on the passed `WorkingContext`.
- The Context Compiler MUST also populate the **Memory layer** (`list[DecisionMemoryEntry]`) with prior rejections and decision history for this passenger before each invocation.

## 3. Data Ontology & Boundaries

All data structures flowing across the Kernel/User boundary MUST be strictly typed using **Pydantic v2**. Raw dictionaries are forbidden for domain objects.

- **`WorkingContext`**: Must encapsulate `FlightDelayEvent`, `PassengerTicket`, `CompensationPolicy`, and the passenger's current `WalletBalance`. Must include the `ContextSnapshotID`.
- **`RefundProposal`**: The structured business intent generated by the Agent. Must contain `passenger_id`, `amount_eur`, `reason_code`, and `policy_ref`.
- **`ProofCarryingIntent`**: The final payload from the Agent to the Kernel. Must wrap the `RefundProposal` and append:
  - `dfid` (DecisionFlow ID)
  - `context_ref` (matching `ContextSnapshotID`)
  - `evidence_hash` (binding the flow, state, contract, and rules)
  - `roa_signature` (Agent's cryptographic identity signature)

## 4. Conflict Resolution Hierarchy

If generation rules conflict, the Context Compiler Pattern mandates this strict evaluation hierarchy:

1. **Threat Model** (`3_threat-model.md`) - Absolute security overrides.
2. **Boundaries** (`2_dir-boundaries.md` - this file) - Structural and architectural invariants.
3. **Coding Standards** (`5_coding-standards.md`) - Implementation patterns.
4. **Intent & Acceptance Criteria** (`1_intent.md`, `4_acceptance-criteria.md`) - Business logic requirements.

*Architectural integrity (Layers 1 & 2) always supersedes feature delivery (Layer 4).*
